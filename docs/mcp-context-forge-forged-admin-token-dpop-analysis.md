# Nine Token Thefts, One Missing Control

The ninth theft didn't steal a token at all — it minted one. IBM's ContextForge is an MCP gateway and administrative platform (`mcp-contextforge-gateway` on PyPI, 1.0.0): the layer that sits between your AI agents and every registered MCP tool, server, prompt, and resource, across every team and tenant. Versions before 1.0.2 shipped CVE-2026-53709, published October 13, 2026, CRITICAL: a hardcoded HMAC-SHA256 signing key (`JWT_SECRET_KEY`, defaulting to a literal test string) baked into both `mcpgateway/config.py` and the project's own `.env.example` — the file the docs tell operators to copy as `.env` on first install.

The chain, per GHSA-m8rv-5m6m-32ff: `verify_jwt_token()` accepts HS256 tokens signed with that public key material, with no database lookup, no JWKS, no pinning. And `get_current_user()` contains a platform-admin bootstrap branch: when the token's `sub` matches `PLATFORM_ADMIN_EMAIL` (default `admin@example.com`) and `REQUIRE_USER_IN_DB=false` (also the default), the gateway synthesizes a virtual platform-admin user on the spot — `is_admin=True` hardcoded, no DB row required. Any party who can read the public repository can forge an admin token with a twenty-line Python script. Unauthenticated. Network-reachable. Deterministic.

Two details make this one sting. First, the forgery survives everything: deleting the admin account, rotating passwords, revoking sessions — none of it matters, because each fresh token rebuilds the admin from claims. The attacker's access has no account state to delete. Second, the project's own `SECURITY.md` boasts Snyk custom rules that "enforce detection of hardcoded JWT secrets" as a supply-chain policy — the project classified this exact pattern as a vulnerability while shipping it as the configured default for the production package. A warning is logged when the weak key is in use; startup is not blocked, token signing is not blocked. The only documented mitigation (`REQUIRE_USER_IN_DB=true`) ships with a warning that it will lock operators out of fresh deployments — a structural disincentive to turn it on. The fix is version 1.0.2.

It was not the week's only minted admin. One day later, CVE-2026-110612 landed on wwwlike/vlife, a Java low-code platform: its `TokenUtil` carries a hardcoded HS256 signing key — in the public repository — and an unauthenticated attacker who reads it signs tokens with `superUser=true` and arbitrary `groupIds` claims to take super-administrator access on any URL of any vlife instance through 2.0.1 (CWE-321, per VulnCheck's NVD entry). Different stack, different vendor, different corner of the ecosystem — the same twenty-line forgery, the same indistinguishability. Three minted-admin CVEs in two days, counting this series' eighth: the hardcoded key is having a week.

Different app, different bug, identical failure mode — the ninth time in this series, and the purest expression of it: a bearer credential that anyone can produce, and a server that cannot tell the forger from the owner from the thief. The attacker never breaks crypto either; they just read the repository.

To be precise about what DPoP can and cannot do here: RFC 9449 would not have fixed either hardcoded key — replacing them with cryptographically random secrets is the patch, full stop. But notice what the vulnerability really is. Authentication here reduces to "present a correctly-signed string," and the forged string is byte-for-byte indistinguishable from a legitimate admin's. That indistinguishability is the whole disease: theft, leak, and forgery are all the same event to a bearer-token server. Sender-constrained tokens break the equivalence. With DPoP, possession of the token string is never sufficient — the proof key never leaves the client, so a token that can be copied, leaked, dumped, or minted is not a credential. The forged token still has to be presented, and presentation requires the key. The key rotation closes this hole; the control converts the entire class of "the string is the identity" failures into failures that require stealing an actual private key. Anywhere a bearer credential is the whole of authentication, binding it to the holder is the missing control.

I maintain pydpop ([github.com/eaakun/PyDPoP](https://github.com/eaakun/PyDPoP), `pip install pydpop`): a pure-RFC 9449 DPoP library for Python — ES256 proof generation plus full server-side verification, drop-in integrations for httpx/requests/aiohttp and FastAPI/Django/Flask/Starlette, post-quantum hybrid algs, v0.2.1 on PyPI, [live demo](https://huggingface.co/spaces/tatkuen/pydpop-demo). If this month sent you rotating secrets, DPoP is the control that makes the next theft a non-event.
